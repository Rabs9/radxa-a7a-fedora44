# Item E: speed of the open stack, measured 2026-09-10

Board: `fedora-6.6.98-a7apvr.202609091821` (upstream-master drm/imagination graft), GPU 1008 MHz @ 800 mV, runtime
power-down on, tuned `throughput-performance` (little 2.8 GHz, big 3.0 GHz, governor `performance` on both
clusters), six a7a RPMs installed, `a7a-gpu-check` 0 fail / 0 warn. Display 1024x600, scanout AB30.

Rules for this session: measure first, one change at a time, re-measure, keep what helps, revert what does not,
every number lands in this file.

## The measurement harness

`tools/gpu-debug/speed-bench.sh` (new, runs on the board inside the logged-in session):

| mode | what it reports |
|---|---|
| `client [reps] [sizes]` | glmark2 build scene per window size: client fps + KWin ms CPU per composited frame |
| `full [--all] [reps] [size]` | glmark2-es2-wayland build / texture / Score (build+texture scenes only unless `--all`) |
| `threads [pid]` | which CPU each thread of a process ran on last (0-5 little, 6-7 big) |
| `idle` | clocks, governors, GPU power state, IRQ affinity, temperatures |

Every mode discards a warm-up run first. **That warm-up is not optional**: see the first finding below.

### Finding 0: `a7a-gpu-check --bench` reports a fake first number

The very first `a7a-gpu-check --bench` of this session printed `640x480: FPS: 15` and `1024x600: FPS: 35` — the
small window *slower* than the big one, which is impossible. With a discarded warm-up run the same board gives
271 fps and 34 fps. The 15 fps is the cost of the first client after an idle period: the GPU cold-boots out of
runtime suspend and Mesa compiles the load-op/render-state programs that the caches then hold. `a7a-gpu-check
--bench` has no warm-up, so its 640x480 figure is only trustworthy if something else has just used the GPU.
Fixed in `tools/board/a7a-gpu-check` (a discarded warm-up run per size).

## Baseline (2026-09-10, before any change)

Median of 3 runs, desktop idle, no other windows open (the 2026-09-09 note "bench numbers halve with windows
open" still applies — measure on a clean desktop).

| metric | baseline |
|---|---|
| glmark2 client 640x480 | **271 fps**, KWin **1.3 ms** CPU per composited frame |
| glmark2 client 1024x600 | **34 fps**, KWin **12.6 ms** CPU per composited frame |
| glmark2-es2-wayland 640x480 | build **309**, texture **394**, Score **351** (build+texture scenes) |
| glmark2-es2-wayland 640x480, whole suite | Score **193** (all scenes; ~5 min/run, kept for reference only) |
| SuperTuxKart `--benchmark` (black_forest replay, 762 frames) | **4.1 fps**, median frame **242.7 ms** |

The 2026-09-09 reference in the next-session prompt was "640x480 ~250-280 fps / 1 ms; 1024x600 ~40 fps / 8-12 ms;
glmark2 client ~270/360/300". 640x480 and the glmark2 scenes reproduce (the scenes are a little better than the
09-09 note). 1024x600 sits at the bottom of its range: 34 fps / 12.6 ms against 38-46 fps / 8-12 ms.

### SuperTuxKart per-frame CPU breakdown

From STK's own profiler CSV (`~/.config/supertuxkart/config-0.10/stdout.log.profile-black_forest-cpu-0.csv`,
medians over all 762 frames):

| section | median per frame |
|---|---|
| Main loop | 242.7 ms |
| IrrDriver update (all rendering) | 235.4 ms |
| — of which drawAll() | 109.1 ms |
| Update race (game logic + physics) | 4.8 ms |

**97 % of the frame is CPU time inside the GL/driver path**, and only 2 % is the game itself. The companion GPU
CSV is all zeros: the driver exposes no timer queries (`pipelineStatisticsQuery = false`), so STK cannot measure
GPU time. The game is not GPU-bound — it is bound by per-draw driver overhead on the CPU, the same bottleneck
that the three Mesa caches attacked in KWin on 2026-09-09.

## Finding 1: the game runs on SuperTuxKart's fixed-function fallback renderer

Owner, watching the benchmark: *"looks terrible. both graphics and fps"*. Both halves have one cause.

```
IrrDriver: OpenGL renderer: zink Vulkan 1.2(PowerVR B-Series BXM-4-64 MC1 (IMAGINATION_OPEN_SOURCE_MESA))
IrrDriver: OpenGL version: 2.1            OpenGL ES 2.0 Mesa 26.1.8
warn: irr_driver: Using the fixed pipeline (old GPU, or shaders disabled in options)
warn: OpenGL: OpenGL version is too old!
```

`eglinfo` on every platform (GBM, Wayland, surfaceless, device), EGL driver `powervr`:
**OpenGL compatibility 2.1, OpenGL ES 2.0**. The same board's `swrast`/llvmpipe device reports OpenGL 4.6 and
OpenGL ES 3.2, and the DDK reaches GLES 3.2 on this silicon — so this is our Mesa stack, not the hardware.

STK 1.5 needs GL 3.3 or GLES 3.0 for its modern renderer; at 2.1/ES 2.0 it falls back to Irrlicht's fixed
pipeline, which both looks worse and issues far more small draws — feeding straight into the per-draw overhead
measured above.

### Why zink stops at ES 2.0 (measured, not guessed)

zink hardcodes `caps->glsl_feature_level = 460`, so the cap is not zink's own. Mesa computes the ES version in
`src/mesa/main/version.c` (`_mesa_compute_version_es`, `ver_3_0`) from a list of extension flags. Of that list,
the PowerVR device exposes 251 GL extensions and is missing exactly **two**:

| missing | needs | cost |
|---|---|---|
| `GL_EXT_transform_feedback` | `VK_EXT_transform_feedback` | **not implemented at all**: `grep -rl transform_feedback src/imagination/vulkan/` finds nothing, and `vulkaninfo` shows the extension only on llvmpipe (GPU id 1), not on the PowerVR device |
| `GL_ARB_uniform_buffer_object` | `MaxUniformBlockSize >= 16384` **and** >= 12 uniform blocks in the vertex *and* fragment stage | PowerVR reports `maxUniformBufferRange = 16384` (exactly the gate) and `maxPerStageDescriptorUniformBuffers = 12` (the Vulkan minimum). zink takes `MIN2(maxPerStageDescriptorUniformBuffers, PIPE_MAX_CONSTANT_BUFFERS)` and spends one slot on GL's default uniform block, so GL sees 11 < 12 |

So the UBO half may be a limits change in the PowerVR Vulkan driver (if the hardware really allows more than 12
uniform buffers per stage — to be checked against the DDK, which does expose ES 3.2). The transform-feedback half
is a full `VK_EXT_transform_feedback` implementation on Rogue streamout: a project of its own, far larger than
Item E, and **both** are required before ES 3.0 appears. Desktop GL 3.0 is further out still (it additionally
needs `ARB_texture_compression_rgtc`, and `textureCompressionBC = false` on this hardware).

> **Correction (2026-09-10 night, `a7a-gpu-gap`, docs/GPU-GAP-2026-09-10.md):** the RGTC sentence above is wrong.
> `GL_ARB_texture_compression_rgtc` is listed in the open stack's GL 2.1 context (Mesa emulates RGTC without BC
> hardware), and Mesa's own GL 3.0 gate, evaluated term by term against every flag the stack computes, fails on
> `EXT_transform_feedback` alone. The two ES 3.0 terms above are confirmed exactly.

Recorded as a finding, not started. Owner's call.

## Finding 2: do not benchmark at 1024x600 — it is bimodal

The first A/B runs at 1024x600 kept flipping between ~41 fps / 7.5 ms and ~35 fps / 12 ms, sometimes inside one
set of three repeats. 1024x600 is exactly the screen size, so the result depends on whether KWin promotes the
window to a scanout plane (barely composites) or composites it — and, as 1(b) below shows, on where KWin's threads
happen to be at that moment. **1000x560 is the same compositing work and is stable to ±1 fps** (34/34/33/34/34
over five repeats), so every A/B below uses 640x480 and 1000x560. The 09-09 range "1024x600 38-46 fps" and
today's baseline 34 fps are the two modes of the same thing, not a regression.

## Changes tried

### 1(a) GPU interrupt affinity — KEPT (small)

`/proc/interrupts` showed all 2.69 M GPU interrupts on **cpu0**: the mask was 0-7, but the kernel routes a level
interrupt to the first CPU in the mask, and cpu0 is a little core. Three independent A/B pairs, medians of 3:

| irq 484 | 640x480 | 1000x560 |
|---|---|---|
| 0-7 (default → cpu0, little) | 267-271 fps / 1.4 ms | 34 fps / 12.1 ms |
| **6-7 (big cluster)** | **277-280 fps / 1.3 ms** | 34 fps / 12.1-13.1 ms |

+3.7 % on the small window, nothing measurable on the large one — as expected, since that frame is dominated by
KWin's own CPU time in the driver, where interrupt latency is a rounding error. cpu6 alone and cpu7 alone are
within noise of each other (277 vs 268), so the mask is `6-7`: it keeps the interrupt off the little cluster and
still works if cpu6 is offline. Free and deterministic, so kept. Shipped as a udev rule in `a7a-gpu-tools`.

### 1(b) KWin on the big cores — KEPT (large)

The first snapshot of `ps -L -o psr` showed KWin's main thread on cpu6 and suggested there was nothing to win
here. That was a snapshot: **the thread wanders**. Later samples found it on cpu2, and the fps followed it.

Forcing the two states apart (medians of 3, a full discarded bench run per arm first so threads have migrated):

| kwin_wayland affinity | 640x480 | 1000x560 |
|---|---|---|
| little only (0-5) | 262 fps / 1.5 ms | 33 fps / 13.8 ms |
| **big only (6,7)** | **293 fps / 0.8 ms** | **39 fps / 7.0 ms** |
| default 0-7 | 277 fps / 1.4 ms | 34 fps / 12.3 ms |

**+11.8 % fps at 640x480 and +18 % fps with half the compositor CPU at 1000x560.** The default 0-7 sits at the
bottom of that range from cold and climbs toward the top only after sustained load: an A/B/A run measured
277 → 295 → 288 fps, i.e. unpinning did *not* return to the starting number, because once sustained load has
migrated the threads to a big core they stay there. So the default costs both throughput and predictability, and
it is the same mechanism behind Finding 2's bimodal 1024x600 and behind "sometimes normal, sometimes turtle".

Durable form: `CPUAffinity=6-7` in a drop-in for `plasma-kwin_wayland.service`, shipped in `a7a-gpu-tools`
(not `taskset`, which is lost the next time KWin restarts).

### 1(c) thermal — NOTHING THERE

Sampled every 10 s through a full SuperTuxKart benchmark run (the heaviest load available):

```
cpub=44-49  cpul=45-48  gpu=42-46  ddr=41-46  skin=33      (degC)
cpu0 = 2800 MHz and cpu6 = 3000 MHz at every sample, never once below
dmesg: 0 lines matching thermal|throttl|cpufreq.*limit
```

No throttling, no clock drop, ~50 degC peak with a 33 degC skin. The board has a lot of thermal headroom at the
pinned clocks, so `schedutil` on the little cluster is not needed and nothing here is limiting speed. It also
means Item D's 1200 MHz is not going to be blocked by heat.

### The game: big-core pinning does almost nothing

SuperTuxKart `--benchmark` (black_forest replay, fixed 762-frame workload, so wall time is the metric):

| run | time | fps |
|---|---|---|
| baseline | 184 270 ms | 4.13 |
| KWin pinned 6,7, game unpinned | 180 543 ms | 4.22 |
| KWin pinned 6,7, game pinned 6,7 | 177 845 ms | 4.29 |

+1.5 % for pinning the game, +2 % for pinning KWin. Both are noise next to the 242 ms frame. The compositor wins
big from the big cores and the game does not, because the game runs under sustained load, which is exactly the
condition in which the scheduler already parks its render thread on a big core. Nothing to ship here.

## Finding 3: forcing GLES 3.0 gets SuperTuxKart's modern renderer to start, but it renders black

The cheap test of whether the modern renderer could work at all on this driver, before spending weeks on
transform feedback:

```
MESA_GLES_VERSION_OVERRIDE=3.0 MESA_GL_VERSION_OVERRIDE=3.3COMPAT MESA_GLSL_VERSION_OVERRIDE=330 supertuxkart ...
```

The version lie is accepted all the way through:

```
IrrDriver Logger: Using renderer: OpenGL ES 3.0 Mesa 26.1.8
IrrDriver: OpenGL version: 3.0            OpenGL version string: OpenGL ES 3.0 Mesa 26.1.8
```

The "Using the fixed pipeline" and "OpenGL version is too old!" warnings are **gone**, the ES 3.0 extension list
grows by ~45 entries (`EXT_copy_image`, `OES_sample_shading`, `EXT_draw_buffers_indexed`, `EXT_color_buffer_float`,
`EXT_texture_compression_rgtc`/`bptc`, `OVR_multiview`, ...), and STK loads and compiles its modern shader set
(`sp_pass.vert`, `motion_blur.frag`, `transparent.frag`, ...) instead of falling back.

**But the screen is black.** The renderer starts and produces no image. That is the expected outcome of an
override: the version is a claim, not an implementation, and the two extensions Mesa's gate actually wanted are
still missing underneath — `EXT_transform_feedback` above all, which the pvr Vulkan driver does not implement in
any form.

So the answer to "can the modern renderer run on this driver at all" is **no, not today**, and a per-application
`drirc` entry would only make a black screen permanent. This closes the cheap path: GLES 3.0 on the open stack is
a driver project (transform feedback is weeks, not hours), not a configuration change.

**The honest position for games today is the vendor stack.** Same board, one reboot (`backtoddk.sh`): the DDK
gives GLES 3.2 and roughly twice the GL throughput (zink over the vendor Vulkan blob measures glmark2 off-screen
661 against ~380 for Mesa's driver), at the price of X11 and per-app settings. Both stacks are packaged and
switch with one command, and `a7a-gpu-session.service` moves the session config across by itself, so this is a
choice per use, not a rewrite.

The per-draw CPU work in the Mesa driver stays worth doing either way: it is 97 % of the game's frame and it
helps every application on the open stack, whatever GL version they get.

### What shipped

Both in `a7a-gpu-tools` (built and `dnf install`ed on the board, `rpm -V` clean, 226 tests green):

- `/usr/lib/udev/rules.d/90-a7a-gpu-irq.rules` + `/usr/local/bin/a7a-gpu-irq-affinity` — GPU interrupt to the big
  cluster on every `powervr` bind. Verified live: `irq 484 -> cpu 6-7 (effective 6)`.
- `/etc/systemd/user/plasma-kwin_wayland.service.d/a7a-cpu-affinity.conf` — `CPUAffinity=6-7` for the session
  compositor. Verified parsed (`systemctl --user show plasma-kwin_wayland.service -p CPUAffinity` -> `CPUAffinity=6-7`);
  **takes effect at the next login**, and until then the running KWin holds the same affinity from a `taskset`.
- `a7a-gpu-check --bench` gained its warm-up run, and `tools/gpu-debug/speed-bench.sh` is the fuller harness.
