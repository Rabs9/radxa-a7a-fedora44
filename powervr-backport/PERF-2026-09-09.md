# The compositor penalty was mine, and the driver is too old for the firmware

**2026-09-09.** Two results, one good and one that sets the next task.

## 1. The 8.5x compositor penalty was a missing kernel option

| | glmark2 |
|---|---|
| off-screen GBM, no compositor | 207 |
| on-screen GBM, straight into scanout buffers | 200 |
| Wayland client through KWin, **without** `cap_sys_nice` | **24** |
| Wayland client through KWin, **with** `cap_sys_nice` | **133** |
| same, fullscreen | 131 |

Two things fall out of that.

**The linear-scanout theory was wrong.** 207 off-screen versus 200 rendering
straight into scanout buffers is a 3% difference. The display plane accepting
only `DRM_FORMAT_MOD_LINEAR` costs almost nothing here - the tiled-to-linear
conversion I blamed for the loss is not where the time goes. The experiment that
settled it: `glmark2-es2-gbm` with and without `--off-screen`, compositor
stopped so it could hold DRM master.

**The real cause was the compositor running without real-time priority**, at
5.5x. And that was self-inflicted: the backport kernel was built from the Debian
board's config, which lacks `CONFIG_EXT4_FS_SECURITY`. Without it `setcap`
fails, so `kwin_wayland` cannot carry `cap_sys_nice`, so KWin never gets RT
scheduling. a7a-fedora `ca5f111` had already fixed this for this board; the
backport quietly reintroduced it.

With it fixed, the stack looks healthy: 207 raw, 200 to scanout, 133 through a
full compositing desktop. A ~35% compositor cost is ordinary.

The remaining gap to the DDK's 1267 is the zink-over-Vulkan userspace, not the
kernel or the display path.

## 2. The driver is older than the firmware

During the fullscreen run:

```
powervr 1800000.gpu: Job timeout                          x116
powervr 1800000.gpu: [drm] Received unknown FWCCB command 2abc006b
```

FWCCB is the firmware-to-host command channel. The firmware is sending commands
this driver does not know.

That is a version mismatch, and the direction is clear:

- firmware: `v1.1 build 6976702`, from Imagination's April 2026 staging drop
- driver: `drm/imagination` as of **v6.8**, dated `20230904`

v6.8 was chosen deliberately - it is the smallest backport onto 6.6, and
`pvr_drm.h` is byte-identical from v6.8 to v6.16 so Mesa could not tell the
difference. But the UAPI being frozen says nothing about the *firmware*
interface, which has clearly moved.

### Next: rebuild on the v6.16 driver

Reasons it should be the fix:

- it is contemporary with this firmware drop
- `img,img-rogue` is already in its `dt_match`, so that patch disappears
- BXM-4-64 support was merged upstream for the LicheePi 4A / TH1520, which is
  the same GPU model as ours
- the UAPI is unchanged, so Mesa needs nothing

Cost: more API drift from 6.6 than v6.8 had, so the 46-line adaptation grows.
The method is proven, and the tree is already set up.

Until then, expect job timeouts under sustained load. The desktop survives them
- the screen goes black and comes back with
`systemctl restart plasmalogin.service` - but it is not a stable configuration.
