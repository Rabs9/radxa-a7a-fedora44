## Method and caveats

- A flag counts as present when any context lists one of its extension strings, as absent only when a context in which Mesa would list it (extensions_table.h: API column and minimum version) does not; otherwise it is `?`. The override probe (`MESA_GL_VERSION_OVERRIDE=4.6COMPAT MESA_GLES_VERSION_OVERRIDE=3.2`, set for that probe process only) exists to make every flag observable; it is a read of Mesa's internal state, never a capability claim, and nothing an application runs uses it.
- The vendor DDK is not Mesa: its GL/GLES versions come from its own version strings, and "DDK says yes" for a Vulkan item comes from the DDK's own Vulkan driver (pvr-run).
- Mesa's gates are Mesa 26.1.8's; zink's mapping of Vulkan to GL (GL_FLAG_NEEDS in the tool) cites the 26.1.8 source lines it was read from.

## Transform feedback: where the GLES 3.0 work stops (size estimate)

With patch 6 the only term left in Mesa's ES 3.0 gate, and the only term of the GL 3.0 gate, is
`EXT_transform_feedback`, which zink exposes only on top of `VK_EXT_transform_feedback` (zink_screen.c:952-956,
st_extensions.c:1128). The ranked list above simulates the gates with each item fixed: with the UBO limit alone GLES
stays 2.0; with transform feedback as well, Mesa's gates give GLES 3.1 and GL 3.2 (ES 3.1's own terms already pass).

What the vendor stack says: its **Vulkan driver does not expose transform feedback either**, but its GLES 3.0/3.2
implements it, so the hardware can do it. Its GLES also exposes 35 shader-storage blocks in the vertex stage
(`GL_MAX_VERTEX_SHADER_STORAGE_BLOCKS`), so the hardware can store from vertex shaders.

What exists (2026-09-10): no `VK_EXT_transform_feedback` code in `src/imagination` (Mesa 26.1.8 and main), no merge
request. Mesa's common `src/poly` (in 26.1.8 already: `poly_nir_lower_vs.c`, `poly_nir_lower_gs.c`,
`poly_nir_lower_tess.c`, `poly_nir_passthrough_gs.c` and OpenCL-C helpers; AGX's geometry/tessellation emulation
made common by Collabora in 2025-10, used by Asahi's drivers) emulates geometry shaders, tessellation and transform
feedback with compute pre-passes; its state (`geometry.h`) holds the transform-feedback counters and buffer pointers.

What the open driver lacks for either route (measured): `vertexPipelineStoresAndAtomics`, `fragmentStoresAndAtomics`,
`shaderInt64`, `bufferDeviceAddress`, `geometryShader`, `tessellationShader` are all false; compute with storage
buffers, `multiDrawIndirect` and `drawIndirectFirstInstance` are there.

Two routes:
1. Native: lower transform-feedback outputs to buffer stores in the vertex stage (plus primitive order for strips and
   fans, counter buffers for pause/resume, primitives-written queries, rasterizer discard). Needs vertex-stage stores
   in the pco compiler and the driver; the DDK's 35 vertex SSBOs say the USC can do them.
2. poly: the compute-based emulation. Needs 64-bit global addressing in pco (poly's structures are device pointers;
   `shaderInt64` and `bufferDeviceAddress` are false today), indirect dispatch and a vertex-as-compute path.

Estimate: a driver-and-compiler project of several weeks either way (an estimate, not a measurement: 4-8 weeks for
someone who already knows the pvr driver and pco), plus validation with `dEQP-VK.transform_feedback.*` and piglit's
`EXT_transform_feedback` tests through zink. It is not a configuration change, and a version override only produces
the black screen measured on 2026-09-10 (docs/SPEED-2026-09-10.md, Finding 3). **This is where the GLES 3.0 work
stops for now.**
