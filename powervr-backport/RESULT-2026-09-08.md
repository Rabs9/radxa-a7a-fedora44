# The in-tree PowerVR driver runs on the A733. The firmware is a different product.

**2026-09-08, on hardware.** The backported driver was booted on the Fedora
board and loaded by hand. Result:

```
powervr 1800000.gpu: [drm] loaded firmware powervr/rogue_36.56.104.183_v1.fw
powervr 1800000.gpu: [drm] *ERROR* Unsupported fw info version 2
powervr: probe of 1800000.gpu failed with error -22
```

That is a **success and a hard stop in the same three lines**, and it settles a
question that structural comparison alone got wrong.

---

## What is now proven to work

Everything except the firmware itself.

- **The driver binds the Allwinner GPU node.** `powervr 1800000.gpu` - the
  `img,img-rogue` compatible matched, the platform driver probed.
- **Clocks resolve.** The appended duplicate `core`/`sys`/`mem` phandles work;
  the CCU has no objection to a clock being claimed twice.
- **The reset deassert works.** No error from the code added to `pvr_probe()`.
- **MMIO and power are fine, and this is the strong one.** The driver builds the
  firmware filename from the BVNC it reads out of the GPU's own ID register. It
  asked for `rogue_36.56.104.183_v1.fw` - our exact silicon. It could only do
  that by successfully powering the GPU and reading a hardware register. So the
  worry about the power island was unfounded: reset plus clocks really is the
  whole sequence on this SoC.
- **Firmware loading works.** It found and read the blob.

No crash, no hang, no kernel taint. The board rebooted cleanly afterwards.

## Where it stops, and why the earlier read was wrong

Decoding the 4K info trailer of both blobs with the driver's own
`struct pvr_fw_info_header`:

| field | ours (BSP 36.56.104.183) | linux-firmware (36.52.104.182) |
|---|---|---|
| `info_version` | **2** | **3** |
| `header_len` | 40 | 48 |
| `bvnc` | 0x240038006800b7 = 36.56.104.183 | 0x240034006800b6 = 36.52.104.182 |
| `flags` | **0x80020810** | **0x00000001** |
| `fw_version` | **24.2** build 6603887 | **1.1** build 6976702 |
| `layout_entry_num` / `_size` | 6 / 24 | 6 / 24 |
| `fw_page_size` | 4096 | 4096 |

The driver's gates:

```c
#define PVR_FW_INFO_VERSION            3
#define PVR_FW_FLAGS_OPEN_SOURCE       BIT(0)
#define FW_MAX_SUPPORTED_MAJOR_VERSION 1

if (header->info_version != PVR_FW_INFO_VERSION)           -> reject
if (!(header->flags & PVR_FW_FLAGS_OPEN_SOURCE) ||
    header->fw_version_major > FW_MAX_SUPPORTED_MAJOR_VERSION) -> reject
```

Ours fails all three:

- info version 2, not 3
- `flags & BIT(0)` is **0** - it is **not** the open-source firmware
- firmware version **24.2**, and the driver accepts major version 1 only

`24.2 build 6603887` is not a coincidence: it is exactly the version string the
DDK's GLES reports, `OpenGL ES 3.2 build 24.2@6603887`. This is the DDK's own
firmware.

### The correction

An earlier note in this repo concluded that linux-firmware's `rogue_*_v1.fw`
files "are DDK `rgx.fw` files under a new name." **That was wrong**, and this
run is what disproves it.

The structural evidence was real - identical ELF32/MIPS layout, identical entry
point, 19 identically named sections, byte-identical Codescape 4.9.0 toolchain
string - because Imagination builds both with the same toolchain into the same
container. But they are **two different firmware product lines**:

- **DDK firmware**, version 24.x, proprietary host/firmware ABI, shipped in the
  BSP, driven by `pvrsrvkm`.
- **Open-source firmware**, version 1.x, `PVR_FW_FLAGS_OPEN_SOURCE` set, a
  different and much simpler host interface, driven by `drm/imagination`.

The `_v1` in `rogue_<BVNC>_v1.fw` is not a file revision. It is
`fw_version_major` - the open firmware's major version. That is why all three
published blobs are `_v1`.

So no repackaging, header rewrite or version-check patch can bridge this. The
CCB/KCCB command protocol the in-tree driver implements is the open firmware's,
not the DDK's. Forcing the header past the check would hand the GPU microcode it
cannot execute against a host that speaks a different protocol.

## What this does to the ask

It makes it exact, empirical, and very small.

> The A733's BXM-4-64 works with the in-tree `drm/imagination` driver. We booted
> it: the driver binds the node, brings the GPU up, reads BVNC 36.56.104.183 out
> of the ID register, and requests
> `powervr/rogue_36.56.104.183_v1.fw`. That file does not exist, because the
> open-source firmware build for this BVNC has never been published.
> linux-firmware carries 33.15.11.3, 36.52.104.182 and 36.53.104.796. Please add
> 36.56.104.183.

Nothing is being asked for that Imagination has not already done four times over
for other BVNCs. No driver work, no new architecture - the driver's own MIPS
support is what loaded our blob far enough to reject it.

## What is still true about the DDK route

Unchanged and still the only thing that works today: the DDK gives real
acceleration (`glmark2-es2` 136 -> 1267) as long as each application is launched
with the three environment variables. Its four structural limits - no Wayland
EGL platform, no GLX, no glvnd vendor entry point, no `VK_EXT_robustness2` -
remain, and remain unfixable from outside Imagination.

## State of the board

Rolled back. `g_1008_800` is the default again, `pvrsrvkm` is loaded, `card1` is
back, the desktop is accelerated.

Everything for the experiment stays installed and is one command away:

```
sudo a7a-extlinux default fedora-6.6.98-pvr+ && sudo reboot
```

Note that boot has **no GPU at all** - `pvrsrvkm` is not in its module tree and
the in-tree driver refuses the firmware - so the desktop runs on llvmpipe:
correct rendering, very unresponsive. It is a test bench, not a usable session.

## One trap worth recording

The first attempt booted the *old* kernel despite the new entry being marked
default. Cause: U-Boot resolves `fdtdir` + `$fdtfile`, and on this board
`$fdtfile` is `allwinner/sun60i-a733-cubie-a7a.dtb`. Every working entry keeps
its DTB in that vendor subdirectory; the directory created by hand had the file
at the top level. The FDT load failed, U-Boot silently abandoned the label and
fell through to the next one. Mirror the existing layout exactly.
